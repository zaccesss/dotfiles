# Reference

Every tracked preference explained, the key bindings, the themes and what's deliberately not tracked here.

## Where STM32CubeIDE keeps these

Each workspace has its own preferences in `<workspace>/.metadata/.plugins/org.eclipse.core.runtime/.settings/`, one `.prefs` file per plugin, exactly as in Eclipse. They are Java properties files: `key=value` per line, with `=` inside a value written as `\=` and a line break as `\n`. A new workspace starts on STM32CubeIDE's defaults, which is why the merge script takes the workspace path as an argument. With none given it uses the newest `STM32CubeIDE/workspace_<version>` folder in the home folder that has a `.metadata` folder.

Each fragment in [`shared/prefs/`](../shared/prefs/) is named after the file it merges into. Lines starting with `#` are notes and are never written to the workspace.

## `org.eclipse.ui.editors.prefs`

| Key | Value | Why |
| --- | --- | --- |
| `lineNumberRuler` | `true` | Line numbers on, to match compiler errors and line references. |
| `spacesForTabs` | `true` | The Tab key inserts spaces, so code looks the same pasted into a report or another editor. Code generated by STM32CubeMX keeps its own indentation. |
| `tabWidth` | `4` | Four spaces per indent. |
| `highlightCurrentLine` | `true` | Shades the line holding the cursor, so it is easy to find again. |
| `spellingEnabled` | `true` | Spell checks comments and strings. |

## `org.eclipse.cdt.ui.prefs`

| Key | Value | Why |
| --- | --- | --- |
| `spelling_locale` | `en_GB` | British English for the spell checker in C and C++ files instead of the US default. |

The themes add the C syntax and semantic colours to this file, see [Colours](#colours).

## `org.eclipse.ui.workbench.prefs`

| Key | Value | Why |
| --- | --- | --- |
| `SAVE_AUTOMATICALLY` | `true` | Saves open editors on its own. |
| `SAVE_AUTOMATICALLY_INTERVAL` | `20` | Every 20 seconds, so a crash, a flash or a closed lid loses very little. |
| `org.eclipse.ui.commands` | the key binding XML | The 15 user key bindings below. Eclipse stores every user binding in this one value, so it is merged as a whole. |
| `org.eclipse.jface.textfont` | `1\|GeistMono Nerd Font\|14.0\|0\|` | From each platform's `prefs/` overlay (18 points on the Mac). The text font for plain editors and consoles. |
| `org.eclipse.cdt.ui.editors.textfont` | the same | The C/C++ editor's own font, set to the same so C files match. |
| `terminal.views.view.font.definition` | `1\|GeistMono Nerd Font Mono\|14.0\|0\|` | The Terminal's font: the Mono build, whose icons fill one cell. |

The full font string is `version|family|size|style|windowing system|...|native name`, but Eclipse also reads the short form `version|family|size|style|` without the platform part, so one family works everywhere. Only the size differs per platform, since Windows and Linux draw points larger.

## Key bindings

Eclipse writes modifiers as `M1` to `M4` so one binding works on every platform: `M1` is `Cmd` on the Mac and `Ctrl` elsewhere, `M2` is `Shift`, `M3` is `Option` on the Mac and `Alt` elsewhere and `M4` is `Ctrl` on the Mac only. The 15 bindings cover 12 actions, the same keys as the Eclipse setup with the Java actions moved to their C counterparts. They sit on top of the default scheme and bring the VS Code keys already in muscle memory.

| Action | Mac | Windows and Linux | Where it works | STM32CubeIDE's default |
| --- | --- | --- | --- | --- |
| Open resource (find a file by name) | `Cmd+P` | `Ctrl+P` | Everywhere | `Cmd+Shift+R` (`Ctrl+Shift+R`). Print loses `Cmd+P` |
| Quick access (the command palette) | `Cmd+Shift+P` | `Ctrl+Shift+P` | Everywhere, plus a second binding in the C editor | `Cmd+3` (`Ctrl+3`) |
| Delete line | `Cmd+Shift+K` | `Ctrl+Shift+K` | Text editors | `Cmd+D` (`Ctrl+D`) |
| Copy line down | `Shift+Option+Down` | `Shift+Alt+Down` | Text editors and the C editor | `Cmd+Option+Down` (`Ctrl+Alt+Down`) |
| Copy line up | `Shift+Option+Up` | `Shift+Alt+Up` | Text editors and the C editor | `Cmd+Option+Up` (`Ctrl+Alt+Up`) |
| Rename symbol | `F2` | `F2` | C editor | `Shift+Option+R` (`Shift+Alt+R`) |
| Open declaration | `F12` | `F12` | C editor | `F3` |
| Format document | `Shift+Option+F` | `Shift+Alt+F` | C editor | `Cmd+Shift+F` (`Ctrl+Shift+F`) |
| Toggle word wrap | `Cmd+Option+W` | `Ctrl+Alt+W` | Text editors | `Cmd+Option+Y` (`Shift+Alt+Y`) |
| Show in Finder or Explorer | `Cmd+Option+E` | `Ctrl+Alt+E` | Everywhere | None |
| Debug the last launch again | `F5` | `F5` | Everywhere | `F11` |
| Run the last launch again | `Cmd+Shift+F5` | `Ctrl+Shift+F5` | Everywhere | `Cmd+F11` (`Ctrl+F11`) |

Why some need two bindings or a different key:

- **Quick access in the C editor.** The C editor binds `Cmd+Shift+P` to *Go to matching bracket*, which would win over a window-wide binding. A second binding scoped to the C editor takes it back.
- **Copy line in the C editor.** The C editor binds `Shift+Alt+Up` and `Shift+Alt+Down` to its structured selection. A second binding scoped to it keeps copy line the same everywhere.
- **Debug and run.** On a board project the last debug launch builds the project, flashes the board through the ST-LINK and stops at `main`, so `F5` is the one key for a new build on the hardware, as in VS Code. Run does the same without the debugger.
- **`F5` while debugging.** The debugger binds `F5` to *Step Into* in its own context, which is narrower than the window, so `F5` still steps into while the target is paused. *Refresh* loses `F5` and stays in the **File** menu.
- **Run on `Cmd+Shift+F5`.** VS Code uses `Ctrl+F5`, but macOS keeps `Ctrl+F5` for *Move focus to the window toolbar*, so the run binding moves to a key no system shortcut uses. The same file then gives `Ctrl+Shift+F5` on Windows and Linux.

The full binding list as stored, with the command and context ids, is the `org.eclipse.ui.commands` line in [`shared/prefs/org.eclipse.ui.workbench.prefs`](../shared/prefs/org.eclipse.ui.workbench.prefs). **Window > Preferences > General > Keys** shows each with a `U` in the User column.

> [!WARNING]
> `org.eclipse.ui.commands` is one value holding every user binding. Merging it replaces any binding added by hand in that workspace. Add a new binding through the Keys page, then copy the line back into the fragment so the repo keeps up.

## Colours

`shared/theme/` holds the eight Zacess themes for STM32CubeIDE (`Zacess <name>.epf`) and the tab outline files for the two Deep Contrast themes. They are built by [`scripts/build-themes.py`](../scripts/build-themes.py) from the Zacess Eclipse themes in [Zacess Themes](https://github.com/zacesshq/themes) 0.5.0, so the palette and measured contrast are the same:

- **Editor colours** (background, text, selection, current line, line numbers, markers) carry over unchanged.
- **C syntax colours** come from the Java colour that plays the same part: keywords and types from Java keywords, strings and `#include` headers from strings, comments from comments and numbers from Java's number colour.
- **Directives and macros** (`#define`, `#include`, `__HAL_RCC_GPIOA_CLK_ENABLE`) take the colour of Java's `return` keyword, which every theme keeps apart from functions and keywords, so a HAL macro never reads as a function call.
- **Semantic colours** (functions, globals, fields, locals, parameters, enumerators, typedefs) come from the matching Java semantic colours. Doxygen comments take the Javadoc colours.
- **Terminal colours** are written for both Terminal plugins: `org.eclipse.terminal.control`, which STM32CubeIDE 2.2 (Eclipse 4.38) uses for its Terminal view. The older `org.eclipse.tm.terminal.control` covers 2.1.

To rebuild after a Zacess Themes release, point the script at the folder holding the Eclipse `.epf` files:

```bash
python scripts/build-themes.py <folder with the Zacess Eclipse .epf files>
```

The apply scripts merge a theme after the tracked keys: each `/instance/<plugin>/<key>=<value>` line merges into that plugin's `.prefs` file the same way. `org.eclipse.e4.ui.css.swt.theme.prefs` gets the matching workbench theme (`e4_dark` for the dark themes, `e4_default` for the light ones). Zacess Deep Contrast Dark is the default; `--theme <name>` picks another and `--no-theme` skips it.

| Short name | Theme | Workbench |
| --- | --- | --- |
| `deep-dark` | Zacess Deep Contrast Dark | Dark |
| `deep-light` | Zacess Deep Contrast Light | Light |
| `hc-dark` | Zacess High Contrast Dark | Dark |
| `hc-light` | Zacess High Contrast Light | Light |
| `dark` | Zacess Dark | Dark |
| `light` | Zacess Light | Light |
| `cream` | Zacess Cream | Light |
| `yellow` | Zacess Yellow on Black | Dark |

STM32CubeIDE has no setting to follow the system light and dark appearance, so the theme stays fixed. By hand, **File > Import > General > Preferences** imports any `.epf`, then **General > Appearance** picks Light or Dark and STM32CubeIDE restarts.

## Not tracked here

- Debug probe and ST-LINK settings, the toolchain and the STM32Cube firmware repository paths, all written by STM32CubeIDE for each machine.
- Window layout, perspectives, recent files, launch configurations and the tab colours in `org.eclipse.ui.workbench.prefs`.
- STM32CubeIDE's own install settings (`stm32cubeide.ini`) and the projects inside the workspace.
