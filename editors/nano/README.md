# nano

My nano settings: one shared `nanorc` for GNU nano on every machine, VS Code's keys where nano can take them and the ten Zacess themes, switched by `zt` like every other editor. nano's own rc file is written by `zt` per machine rather than linked, for the reasons under [Themes](#themes).

## What it sets

| Setting | Value | Why |
| --- | --- | --- |
| `linenumbers`, `constantshow`, `stateflags` | On | Line numbers, the cursor position on the status line at all times and the mode flags top right, so the place in a file is always on screen |
| `softwrap`, `atblanks` | On | Long lines wrap at a space instead of running off the edge |
| `tabsize`, `tabstospaces`, `autoindent` | 4, on, on | Four spaces, the same as every other editor here |
| `smarthome`, `zap`, `trimblanks` | On | Home goes to the first character, typing over a selection replaces it and trailing spaces go when a line is wrapped |
| `indicator`, `mouse` | On | A scrollbar and mouse clicks for the cursor and the menus |
| `historylog`, `positionlog` | On | Search history and the cursor position come back when a file is reopened |

The file keeps to what nano 6.0 understands, so the packaged nano on any supported Linux (7 or 8 on current Ubuntu and Fedora), Homebrew's and the one inside Git for Windows all read it the same way. nano stops at start on an option it does not know, so nothing newer goes in.

## Keys

| Key | Does | Was |
| --- | --- | --- |
| `Ctrl+S` | Save | Save (nano's own since 4.0) |
| `Ctrl+Q` | Quit, in every menu | Search backwards |
| `Ctrl+Z` | Undo | A hint that `Ctrl+T` then `Ctrl+Z` suspends |
| `Ctrl+Y` | Redo | Page up |
| `Ctrl+F` | Find | Right one character |

nano's own keys stay beside them: `Ctrl+C` shows the cursor position, `Ctrl+X` exits, `Ctrl+O` writes out, `Ctrl+W` searches, `Ctrl+\` replaces and `Ctrl+G` opens the help. `Ctrl+T` then `Ctrl+Z` suspends nano, since `Ctrl+Z` alone is undo here. The bottom two lines list the keys at all times.

## Themes

The colours of the title bar, status line, prompts, key tags, line numbers, selected text, search matches, error messages and the scrollbar come from a colour fragment per Zacess theme in [`terminal/nano/themes`](../../terminal/nano/), generated by [`build-themes.py`](../../terminal/terminal/scripts/build-themes.py) from the palette.

nano accepts its interface colours (`set titlecolor` and the rest) only in its main rc file: a `set` inside an included file is an error, so the fragments cannot be included. An `include` whose pattern matches nothing is an error too, one that makes nano wait for Enter before it starts. So `zt` writes nano's rc file itself on every switch, as one file made of three parts: the shared base in this folder, the chosen theme's `set` lines from its fragment and one `include` line for the syntax folder this machine's nano ships (`/usr/share/nano` on Linux, WSL and Git for Windows, Homebrew's `share/nano` on a Mac). A machine whose nano ships none gets no include line. The first line is a marker, `## zacess theme: <id>`, which `zt current` reads back. `zt doctor` builds the file again in memory and reports drift when the one on disk differs, so a hand edit, a nano upgrade that moves the syntax folder or a change to the base is caught. `zt pin nano <theme>` keeps nano on one theme while the rest follow `zt`. nano reads its files at start, so an open nano keeps its colours until it is reopened. Syntax highlighting uses nano's own definitions, which name the terminal's colours, so it follows the palette the terminal is on.

## Install

| System | nano | The rc file `zt` writes |
| --- | --- | --- |
| macOS | `brew install nano` (in [`shell/mac/Brewfile`](../../shell/mac/Brewfile)). Apple's `/usr/bin/nano` is Pico 5.09, which reads no configuration file at all | `~/.config/nano/nanorc` (or `$XDG_CONFIG_HOME/nano/nanorc`) |
| Linux and WSL | Packaged on Ubuntu and Fedora and installed by [`setup/linux-bootstrap`](../../setup/linux-bootstrap/) | `~/.config/nano/nanorc` |
| Windows | The nano inside Git for Windows, run from Git Bash | `%USERPROFILE%\.nanorc` (`~/.nanorc` in Git Bash) |

Nothing is linked by a bootstrap: run `zt <theme>` once after the bootstrap (or `zt auto`) and the file is written. nano reads `~/.nanorc` first and only then `~/.config/nano/nanorc`, so a stray `~/.nanorc` on a Mac or Linux machine would hide the generated one. Homebrew puts its nano before Apple's on `PATH`, so a plain `nano` is the GNU one once it is installed.

## Check it worked

1. `nano --version` says GNU nano, not Pico.
2. Open a file. Line numbers show on the left, the title bar is in the theme's accent colour and the cursor position is on the status line.
3. Type, then `Ctrl+Z` undoes it and `Ctrl+Y` puts it back. `Ctrl+S` saves without a prompt. `Ctrl+Q` leaves.
4. `zt current` lists nano on the theme `zt` last set and `zt doctor` says the rc file matches what `zt` would write now.

## Validation

`build-themes.py --check` runs in CI and fails when a committed colour fragment is out of date or any text colour in a theme, measured as nano shows it, falls under 4.5:1. The `nanorc` itself is kept to nano 6.0's options and key names by hand. The generated file was started by GNU nano 9.3 on macOS and 8.7 on Ubuntu for every theme with no start-up error.
